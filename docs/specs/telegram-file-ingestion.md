## Anthropic XML Note

Anthropic documentation recommends XML tags for prompt structure, but does not document any canonical built-in semantics for tags such as `<system-reminder>`. For this feature, the runtime will use a repo-local convention with a plain `<system-note>` wrapper instead of relying on undocumented tag semantics.

Primary sources:
- https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/use-xml-tags
- https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices

## Current Runtime Constraint

The current Telegram adapter is text-only:
- The app only registers `filters.TEXT & ~filters.COMMAND`.
- `handle_message()` returns early when `effective_message.text` is absent.
- `FragmentBuffer.add()` also assumes text-only input.
- The runner only accepts a single normalized user string.

Therefore the implementation must normalize Telegram text, captions, attachments, media groups, and voice transcripts into one composed string before agent handoff.

## Goals

1. Accept any Telegram file/media type that can be downloaded by the bot.
2. Download every inbound file to `/tmp/obs-agent/...`.
3. Purge `/tmp/obs-agent` once on daemon/bot startup, not per session or per turn.
4. Preserve enough metadata for the agent to reason about the file.
5. Auto-transcribe Telegram `voice` messages only.
6. Keep transcript delivery internal to the agent by default.
7. Preserve existing Telegram chronological output behavior.
8. Add deterministic unit/integration coverage plus real Telethon live coverage.

## Storage Design

### Temp root

- Root directory: `/tmp/obs-agent`
- Purge timing: once at Telegram bot startup
- Purge scope: remove only `/tmp/obs-agent`, not all of `/tmp`

### Collision handling

Store files in nested directories so filenames can be preserved without collision:

`/tmp/obs-agent/<boot-id>/<chat-id>/<message-or-group-id>/<original filename>`

Notes:
- `boot-id` is unique per daemon/bot startup.
- `message-or-group-id` is the Telegram message id for single messages or media group id for albums.
- The runtime may sanitize the stored filename for filesystem safety, but must preserve the original filename in the injected note.

## Inbound Normalization Contract

Every inbound Telegram message should normalize into a single agent-facing string.

### Plain text only

Pass through the user text.

### Text or caption plus one or more files

Compose:
- the user-authored text/caption first
- then one `<system-note>` block per file

### File-only message

Compose one or more `<system-note>` blocks.

### Voice message

Compose:
- optional user caption if Telegram exposes one
- one `<system-note>` describing the stored voice file
- one `<system-note>` stating transcription status and stored transcript path
- the full transcript text inline below the transcription note

### Voice transcription failure

Compose:
- optional user caption
- one `<system-note>` for the stored voice file
- one `<system-note>` that transcription failed, including the error summary

Also notify the Telegram user that transcription failed and the original file was still attached internally by path.

## Agent-Facing Note Format

The runtime should use a simple, explicit note style rather than many nested XML tags.

Proposed shape:

```xml
<system-note>
Telegram attachment received.
Kind: document
Original filename: report.pdf
Stored path: /tmp/obs-agent/.../report.pdf
MIME type: application/pdf
Size bytes: 12345
</system-note>
```

For voice:

```xml
<system-note>
Telegram voice message received.
Original filename: voice.ogg
Stored path: /tmp/obs-agent/.../voice.ogg
Transcript path: /tmp/obs-agent/.../voice.md
The transcript below was generated automatically from audio and is not user-typed text.
</system-note>

... full transcript text ...
```

## Voice Transcription Pipeline

### Trigger

Only Telegram `voice` messages.

Do not auto-transcribe:
- Telegram `audio`
- documents that happen to contain audio
- videos
- video notes unless explicitly added later

### Command

`/Users/breedoon/Documents/PATH/transcription/transcribe.sh <audio_file> <title> <dest_dir>`

Constraints:
- no diarization flags
- transcript markdown stays in `/tmp/obs-agent/...`
- Whisper JSON may remain under the transcription project temp area

### Title

Use a deterministic sanitized title derived from Telegram metadata, such as the original filename or a generated fallback.

## Media Group Handling

Albums/media groups should be treated as one logical user turn when feasible:
- aggregate all group members
- download all files
- compose one normalized agent input
- include any caption once

If Telegram handler timing makes this impractical, document the fallback behavior here before shipping.

## Telegram User-Facing Behavior

- The user should continue seeing the current chronological markers and agent response flow.
- The transcript text should not be echoed back to Telegram by default.
- If voice transcription fails, send a brief user-visible failure notice.
- Existing outbound Telegram chunk splitting remains relevant for agent responses.

## Open Questions During Build

Record any discovered runtime/API limitations here rather than silently drifting from spec.

- 2026-02-28: The hosted Telegram Bot API can accept large uploads from the user account, but the bot cannot download arbitrarily large files back via `getFile`. In live stress testing with a 105 MB `m4a`, Telegram returned `BadRequest: File is too big`. The runtime now degrades gracefully by surfacing a system note and a user-visible warning instead of crashing. Truly large-file support would require a different ingestion path, such as a local Bot API server or a non-Telegram transfer path.
